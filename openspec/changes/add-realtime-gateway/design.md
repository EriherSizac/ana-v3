# Design

## Context

- Ver proposal.md (Why). Polling actual: desktop v4 `GET /jobs/poll` cada 5 s (`v4/desktop/electron/jobs/poller.ts`, `POLL_INTERVAL_MS`) y `GET /settings` cada 5 min (`electron/settings/remoteSettings.ts`); CLI v3 `GET /get/chats/{agent}/{campaign}` cada 30 s (`v3/cli-whatsapp/index.js`) y `GET /agent/settings` cada 5 min (`remote-settings.js`); ANA Admin sin actualización viva.
- v4 backend: Serverless v4, `ana-backend-<stage>` en us-east-2, HTTP API con authorizer JWT `cognitoJwt`, DynamoDB (`jobs`, `uploads`, `roleperms`, `agents`, `accesscache`…), `resolveUserAccess` (API de Roles + caché) en `src/lib/access.ts`.
- v3 backend: Serverless, mismo nombre de servicio `ana-backend-<stage>` pero en us-east-1, solo S3 (`ana-backend-storage-<stage>`). Las llaves ya codifican destinatario y campaña: `agents/{c}/{agent}-contacts-<ts>.csv` (lo que lee `/get/chats`), `assignments/agents/{c}/{agent}-contacts-<ts>.csv` (pendientes de "Mi asignación"), `agent-publications/{c}/{agent}/`, `review/{c}/{agent}/…`, `rosters/{c}.json`, `uploads/{c}/…`, `config/cli-settings.json`. Agente y campaña en llaves = `normalizeKeySegment` (minúsculas), igual que `cognito:username` del pool.
- Mismo account AWS; mismo pool Cognito para los tres clientes; los tres ya tienen el ID token a la mano (main del desktop vía `TokenBroker`, CLI vía `getIdToken`, navegador vía Amplify `CookieStorage`).
- Otro ingeniero modifica reglas de roles en `v4/backend` en paralelo: el diseño solo consume `resolveUserAccess`.

## Goals / Non-Goals

**Goals:** un solo canal para los tres clientes; latencia de aviso < 2 s; cero cambios de contrato REST y de handlers v3; apagado de emergencia sin release; costo marginal.

**Non-Goals:** enviar datos por el socket; entrega garantizada, replay o historial; mensajería cliente→cliente; presencia de agentes por WebSocket (sigue `POST /agents/heartbeat`).

## Decisions

- **D1. Un solo servicio realtime en el stack v4 (us-east-2), no uno por backend.** v4 ya tiene DynamoDB (registro de conexiones), `resolveUserAccess` (alcance por campaña) y el mismo pool; v3 es solo S3 y agregarle una API WebSocket implicaría duplicar authorizer, tabla y reparto, y que ANA Admin y un agente con desktop+CLI mantengan dos sockets. Alternativas: (a) una API por backend: el doble de piezas y de conexiones; (b) servicio aparte (stack `ana-realtime`): aísla despliegues pero duplica configuración de pool y acceso; se puede extraer después sin cambiar el contrato del cliente (solo la URL). (c) AppSync Events / IoT Core: autorización por canal más rica, pero otro modelo de auth y SDK para tres clientes (uno en Node 18 empaquetado con pkg); API Gateway WebSocket es lo más simple y conocido.
- **D2. Token como subprotocolo, validado por un Lambda REQUEST authorizer en `$connect`.** Los navegadores no permiten headers en `new WebSocket`; las únicas vías son query string o `Sec-WebSocket-Protocol`. Se elige subprotocolo `["ana.v1", idToken]` (un JWT solo usa caracteres válidos de token RFC 6455) porque el query string termina en logs de acceso y en historiales. `identitySource: route.request.header.Sec-WebSocket-Protocol` hace que API Gateway rechace con 401 sin invocar si falta. El authorizer usa `aws-jwt-verify` (`tokenUse: 'id'`, clientId del pool), sin caché de política (cada token es distinto). El handler `$connect` responde `Sec-WebSocket-Protocol: ana.v1` (si no, el navegador aborta). Alternativa: ticket de un solo uso emitido por REST (`POST /realtime/ticket`): evita el JWT en el handshake pero agrega una ruta, almacenamiento de tickets y un viaje extra en cada reconexión; se descarta porque el subprotocolo no se registra en logs de acceso (formato propio sin headers).
- **D3. Origen.** Si llega `Origin`, debe estar en la lista del stage (`REALTIME_ALLOWED_ORIGINS`). `client=admin` exige `Origin`. Desktop (Node 22 de Electron 38) y CLI (`ws` en Node 18) no lo envían. El origen no sustituye al token: impide que una página ajena use el socket del navegador del usuario.
- **D4. Modelo de suscripciones por tema en una tabla.** `ana-backend-realtime-<stage>` (on-demand, TTL `ttl`): items `PK=<tema>, SK=<connectionId>` y uno `PK=conn#<id>, SK=meta` con `{username, client, version, connectedAt, tokenExp, topics[]}`. Temas: `u#<username>`, `k#<client>`, y para `admin` `c#<campaignKey>` por campaña de `UserAccess.campaigns` (`c#*` si trae `*`). Publicar = `Query PK=tema` (para campaña: `c#<c>` ∪ `c#*`), sin Scan. `$disconnect` lee `meta` y borra en lote. TTL = conexión + 3 h por si `$disconnect` nunca llega. Alcance calculado una vez en `$connect`: un cambio de permisos se aplica en la siguiente reconexión (≤ 110 min); aceptable porque los eventos no traen datos (D6). Alternativa: guardar solo `PK=user` y filtrar en el reparto: obliga a Scan para eventos de campaña.
- **D5. Productores → EventBridge → `notify`.** Los handlers v4 llaman `emitRealtime(evt)` (`PutEvents` al bus `ana-realtime-<stage>`, timeout 1 s, errores tragados con métrica `EmitFailed`). Una regla del bus invoca `notify`, que resuelve temas, deduplica connectionIds, envía `PostToConnection` con concurrencia 25, borra 410 y descarta eventos de > 60 s (`MaximumEventAge` 60 s, 1 reintento, sin DLQ: un aviso viejo no vale nada). Alternativa: `PostToConnection` directo dentro de cada handler: más simple pero suma la latencia del reparto a rutas del usuario (`/jobs/ack`, `csvTrigger` con cientos de jobs) y duplica permisos; el bus además es el punto de entrada natural para v3 (D7).
- **D6. Avisos, nunca datos.** Sobre `{v,type,id,at,campaign?,ref?}`, ≤ 1 KB. El cliente responde a cualquier evento (o reconexión) con una lectura REST existente, que conserva authorizer, permisos, roster y campaña. Así no hay que replicar la autorización en el reparto y un evento perdido o duplicado solo cuesta una lectura de más o un retraso hasta el polling de respaldo.
- **D7. Puente v3 por S3 → EventBridge, no por llamadas desde los handlers v3.** Se activa `EventBridgeConfiguration` en `StorageBucket`; una regla en el bus por defecto de us-east-1 filtra `detail.bucket.name` y `detail.object.key` por prefijo (`agents/`, `assignments/agents/`, `agent-publications/`, `review/`, `rosters/`, `uploads/`, `config/cli-settings.json`) y tiene como destino el ARN del bus `ana-realtime-<stage>` de us-east-2 (destino entre regiones soportado, con rol `events:PutEvents`). En v4, una segunda regla (`source: aws.s3`) invoca `notify`, que traduce llave → evento (ver `v3/realtime-bridge`). Ventajas: cubre rutas legadas (`/supervisors/*`), scripts (`setup-campaign.sh`, `upload-to-s3.ps1`) y escrituras futuras sin tocar v3; no agrega latencia ni dependencias a las rutas v3. Alternativas: (a) `lambda:Invoke` asíncrono cross-region desde cada handler v3 a un `notify` v4: hay que editar cada escritor y se escapan los legados; (b) S3 → SNS (us-east-1) → suscripción Lambda en us-east-2: funciona, pero sin filtro por prefijo tan expresivo y sin reutilizar el bus de v4.
- **D8. Latido y duración.** API Gateway corta por inactividad a los 10 min y por duración a las 2 h. Cliente: `ping` al abrir y cada 5 min (la respuesta `pong` trae `exp` del token); reconexión planeada a los 110 min o al renovar el token, abriendo la nueva antes de cerrar la vieja. Servidor: `notify` no entrega a conexiones con token vencido hace > 5 min y las cierra (`DeleteConnection`), así una conexión no vive más que su token más la gracia.
- **D9. Backoff de clientes (contrato común).** Reconexión exponencial con jitter: 1 s, 2 s, 4 s… tope 5 min; tras 403 con razón `disabled` (o 5 rechazos seguidos) tope 15 min. Mientras no hay conexión confirmada (primer `pong`), el cliente usa su polling rápido de hoy; con conexión confirmada usa el respaldo lento (desktop y CLI: 2 min para jobs/asignaciones, 15 min para configuración). Cualquier evento relevante o reconexión dispara una lectura REST inmediata (con coalescencia de 1 s). Los cambios de cada cliente están en sus propios cambios.
- **D10. Interruptor.** Parámetro `realtimeEnabled` (por defecto `true` tras el piloto) → env `REALTIME_ENABLED`. Apagado: el authorizer niega (`disabled`), `notify` descarta, y `realtimeStats` (programada cada 5 min, la misma que publica `ActiveConnections`) cierra las conexiones abiertas. Los clientes, al no tener conexión, vuelven solos al polling rápido: rollback sin release. Cada cliente tiene además su propio flag local (ver sus cambios).
- **D11. Observabilidad.** Métricas EMF en `AnaRealtime` (ver spec), más las nativas de API Gateway (`ConnectCount`, `MessageCount`, `IntegrationError`, `ClientError`). `ActiveConnections` por tipo = `Query Select=COUNT` sobre `k#<client>` cada 5 min. Alarmas: `PostFailed` > 5 % en 15 min, errores de `notify`, errores del authorizer > 10 en 5 min. Access log del stage WebSocket con formato propio sin headers.

## Risks / Trade-offs

- [Nombre de agente legado en la llave distinto del `cognito:username`] → no llega el aviso a ese CLI; recibe la asignación con el respaldo de 2 min. `BridgeSkipped`/eventos sin conexión destino se cuentan para detectar casos.
- [Alcance de campaña congelado hasta 110 min] → los eventos no traen datos y REST revalida; se documenta.
- [Tormenta de reconexiones tras un despliegue o corte] → jitter en backoff; límite de cuenta de 500 conexiones nuevas/s está muy por encima de la flota.
- [EventBridge cross-region añade ~0.5–1 s] → dentro del objetivo de < 2 s.
- [S3 → EventBridge envía todos los eventos del bucket al bus por defecto de us-east-1] → sin costo de entrega para eventos de S3 al bus por defecto; solo se cobran los que la regla reenvía.
- [Reparto con muchos destinatarios (`settings.changed` a toda la flota)] → `Query` paginado y concurrencia 25; para cientos de conexiones son pocos segundos; el evento es raro.
- [Token en el header del handshake] → no se registra en logs propios ni en el access log (formato sin headers); solo viaja por TLS.

## Costo (estimación, us-east-2, precios públicos)

Supuesto: 300 clientes conectados 10 h/día, 22 días/mes. Minutos de conexión: 300 × 600 × 22 ≈ 4 M → ~$1.0 (US$0.25/M). Mensajes: pings 12/h + pongs ≈ 1.6 M + eventos (< 0.5 M) → ~$2 (US$1/M). Lambda (ping, notify, connect) y DynamoDB on-demand: < $2. EventBridge: eventos custom + reenviados < 1 M → < $1. Total ≈ US$5–7/mes. Ahorro: solo el desktop a 5 s hace 720 consultas/h por cliente (HTTP API + Lambda + DynamoDB); bajarlo a 2 min reduce ~96 % de esas invocaciones.

## Migration Plan

1. Desplegar v4 en dev con `realtimeEnabled=true`; probar con `wscat` (subprotocolo) y eventos sintéticos; después la regla y `EventBridgeConfiguration` de v3 en dev.
2. Desplegar v4 y v3 en prod. Sin clientes que se conecten, el único efecto es la publicación de eventos (sin destinatarios).
3. Releases de clientes (cambios `add-realtime-*`), cada uno con su flag local; piloto con una PC/agente antes de abrir a la flota.
4. Rollback: `realtimeEnabled=false` (clientes vuelven a polling rápido en ≤ 5 min); si hiciera falta, quitar la regla de v3. Quitar el stack realtime no rompe ninguna ruta REST.
